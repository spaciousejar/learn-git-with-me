---
title: Commit Message Hooks
description: "Commit-msg hooks validate a commit message before it is written, and are the usual way to enforce a convention."
---
The commit-msg hook runs after you have written a commit message and before Git
records the commit. A non-zero exit aborts the commit, leaving your changes
staged and nothing written.

That makes it the natural place to enforce a convention. Every project that
decides commit messages matter ends up with one of these, or with a commit
lint step in CI that produces the same result more slowly.

## Arguments

```bash
#!/bin/sh
# $1 = path to the file holding the commit message
# $2 = the source of the message: "message", "template", "merge", "squash" or "commit"
```

Check `$2` if you care. `merge` and `squash` messages are generated by Git and
routinely fail a strict pattern, so a hook that rejects them makes merging
impossible.

## Use Cases

- Enforce a `type(scope): description` pattern
- Require an issue reference
- Enforce a line length so `git log` stays readable
- Reject merge commits on a branch that should stay linear
- Detect a leftover `WIP` or a `.only` in the diff

## Example Hook

```bash
#!/bin/sh
# .git/hooks/commit-msg

message_file="$1"
message_source="$2"

# Let Git's own generated messages through
case "$message_source" in
  merge|squash|commit) exit 0 ;;
esac

subject=$(head -1 "$message_file")

pattern='^(feat|fix|docs|refactor|test|chore|perf)(\([a-z0-9/-]+\))?: .{5,72}'

if ! printf '%s' "$subject" | grep -Eq "$pattern"; then
  echo "Commit message rejected."
  echo
  echo "  got:      $subject"
  echo "  expected: type(scope): description"
  echo
  echo "  type is one of feat, fix, docs, refactor, test, chore, perf"
  echo "  description is 5-72 characters"
  echo
  echo "  Example:  fix(auth): redirect to login after token expiry"
  exit 1
fi
```

`head -1` is deliberate. The subject line is what appears in `git log
--oneline` and in release notes, so it is the part worth constraining; the body
is free-form prose and a hook that polices it will be worked around.

## Fixups are better than rejections where you can

A hook that rewrites beats one that refuses. This one lowercases the type and
trims a trailing period, so a near-miss is corrected rather than bounced back:

```sh
fixed=$(printf '%s' "$subject" | sed -E 's/^(Feat|Fix|Docs|Chore):/\1:/' | sed -E 's/\.$//')
if [ "$fixed" != "$subject" ]; then
  printf '%s\n' "$fixed" > "$message_file"
  echo "Rewrote commit message subject to: $fixed"
fi
```

## Sharing it

Hooks in `.git/hooks` are per-clone and untracked, so the convention quietly
becomes optional. Commit the script and point Git at it:

```bash
git config core.hooksPath .githooks
```

Or use a tool that manages this for you, such as commitlint with husky, which
gives you a shareable config and better error messages than a shell script.

Keep in mind that GitHub also validates: a repository with
[commit rules](/docs/5-github/basics/contribution-guidelines) configured will
comment on pull requests whose commits do not match, which catches the case
where somebody's editor skipped the local hook.
